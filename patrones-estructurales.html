No es código para copiar y pegar: es un plano. Como el plano base de una casa, cada constructor lo adapta a su terreno.

Los 23 patrones clásicos se publicaron en 1994 en el libro de Gamma, Helm, Johnson y Vlissides, conocidos como el «Gang of Four» (GoF).

Di: Un patrón no es código que se copia; es una forma probada de organizar clases que ya funcionó en muchos proyectos. Hay tres familias, y hoy nos quedamos con las estructurales.

Señala: la columna oscura. Los patrones también sirven como vocabulario: decir "aquí va un Decorator" ahorra media hora de explicación.

Tiempo: 1 minuto.

Los estructurales deciden cómo encajan las piezas

Como con LEGO: lo importante no es cada pieza, sino cómo se une con las demás.

  • Unen clases y objetos en estructuras más grandes.
  • Prefieren la composición: un objeto que guarda a otro y le delega trabajo.
  • Permiten cambiar una pieza sin romper el resto.

Herencia se decide al compilar

class PedidoExpres extends Pedido {} class PedidoRegalo extends Pedido {} class ExpresConRegalo extends Pedido {}

Una clase nueva por cada combinación.

Composición se arma en ejecución

class Pedido { private Envio envio; private Empaque empaque; }

Un pedido combina las piezas que necesite.

Di: Los estructurales responden una pregunta: cómo unir piezas. Casi todos usan composición, es decir, un objeto guarda a otro y le pasa el trabajo, en vez de heredar de él.

Señala: con herencia aparece una clase por cada combinación; con composición el pedido se arma con las piezas que necesite.

Adapter

Hace que dos interfaces que no encajan trabajen juntas, sin modificar ninguna.

El problema en TechStore

Todo el checkout cobra con pagar(pesos). La pasarela de pagos nueva solo entiende cobrar(centavos), y su código no es nuestro.

Sin Adapter tendríamos que:

  • Reescribir una librería que no es nuestra.
  • Convertir a centavos en cada pantalla que cobra.
  • Tocar el checkout por cada pasarela nueva.

Di: ¿Alguien ha viajado y no ha podido cargar el celular? El enchufe no cambia y el cargador tampoco: se pone un adaptador en medio. En TechStore pasa lo mismo: la pasarela de pagos habla en centavos y nuestro checkout en pesos.

Señala: los tres problemas del recuadro. El que más duele es el último: sin el patrón, cada pasarela nueva obliga a tocar el checkout.

Tiempo: 2 minutos.

  1. Vista completaAvanza con la flecha para recorrer el patrón pieza por pieza.
  2. Paso 1 de 4Target: la interfaz que todo el checkout ya usa. Cobra en pesos.
  3. Paso 2 de 4Adaptee: la pasarela externa. Cobra en centavos y no la podemos modificar.
  4. Paso 3 de 4Adapter: implementa la interfaz de TechStore y por dentro llama a la pasarela. La línea clave hace la traducción.
  5. Paso 4 de 4Cliente: el checkout sigue llamando pagar(85000). No sabe que existe una pasarela externa.

Di: Primero muestra el código completo y luego recórrelo con la flecha: cada recuadro del diagrama se ilumina junto con su parte del código. En el paso 3 detente en la línea clave: toda la traducción está ahí, multiplicar por 100.

Señala: el adaptador implementa la interfaz que espera TechStore y guarda la pasarela como atributo; eso es composición.

Consejo: recalca que la pasarela se guarda como atributo (composición). El adaptador no hereda de ella, así que solo expone pagar().

Tiempo: 4 minutos.

Se usa al integrar

  • Pasarelas de pago y APIs externas
  • Librerías de terceros
  • Código antiguo (legacy) que no se puede tocar

Ventajas

  • No modificas el código que ya existe
  • La conversión vive en un solo lugar

Desventajas

  • Una clase más que mantener
  • Si la clase original es tuya, a veces basta con cambiarla

Un ejemplo de uso

InputStreamReader es un Adapter: recibe bytes de System.in y los entrega como caracteres para que se puedan leer líneas.

new BufferedReader( new InputStreamReader(System.in));

Di: Adapter se usa cada vez que integramos algo que no controlamos: pagos, APIs o código viejo. Su costo es una clase más, y si la clase original es nuestra, a veces es más fácil cambiarla.

Señala: la línea de Java de abajo; casi todos la han escrito para leer datos por consola.

Consejo: en new BufferedReader(new InputStreamReader(System.in)) están los dos patrones: InputStreamReader adapta y BufferedReader decora. Úsalo para conectar con el patrón de Yeison.

Consejo: no lo confundas con Facade. Adapter hace encajar una clase en una interfaz que ya existe; Facade crea una interfaz nueva y más simple para muchas clases.

Bridge

Separa qué se hace de cómo se hace, para que las dos partes crezcan por separado.

El problema en TechStore

Hay 3 avisos (Confirmación, Envío, Promoción) y 3 canales (Email, SMS, WhatsApp). Con herencia, cada combinación es una clase: ConfirmacionPorSms, EnvioPorWhatsApp…

Sin Bridge tendríamos que:

  • Escribir 3 × 3 = 9 clases casi iguales.
  • Crear 3 clases más por cada canal nuevo.
  • Corregir el mismo error en muchas clases.

Di: Piensen en un control remoto universal: el control decide qué hacer y el televisor decide cómo hacerlo. En TechStore tenemos lo mismo: el tipo de aviso y el canal por el que sale.

Señala: el ejemplo de los nombres de clase. Con herencia aparece una clase por cada combinación, y al agregar Telegram serían 3 clases más.

Tiempo: 2 minutos.

  1. Vista completaAvanza con la flecha para recorrer el patrón pieza por pieza.
  2. Paso 1 de 4Implementador: la interfaz Canal. Email, SMS y WhatsApp saben enviar, cada uno a su manera.
  3. Paso 2 de 4Abstracción: Aviso guarda un Canal como atributo. Ese atributo es el puente entre las dos partes.
  4. Paso 3 de 4Avisos concretos: cada aviso arma su mensaje y lo manda por el canal que tenga. La línea clave no sabe cuál es.
  5. Paso 4 de 4Uso: aviso y canal se combinan al crear el objeto. Un canal nuevo es una sola clase, no tres.

Di: Recorran el código con la flecha. Primero los canales, luego el aviso que guarda un canal, y en el paso 3 la línea clave: el aviso solo dice canal.enviar(...) y no sabe si es WhatsApp o Email.

Señala: el atributo protected Canal canal. Esa línea es el puente: es composición, no herencia.

Consejo: haz la cuenta en voz alta: con herencia 9 clases, con Bridge 6. Es lo que más recuerda el público.

Tiempo: 4 minutos.

Se usa cuando algo varía en dos sentidos

  • Avisos × canales de envío
  • Reportes × formatos (PDF, Excel)
  • Figuras × motores de dibujo

Ventajas

  • Evita la explosión de clases
  • Avisos y canales crecen por separado

Desventajas

  • Sobra si solo varía una cosa
  • Hay que planearlo desde el diseño

Un ejemplo de uso

JDBC es un Bridge: tu código usa Connection y el driver de MySQL o PostgreSQL es la implementación que cambia.

Connection c = DriverManager.getConnection( "jdbc:mysql://localhost/techstore");

Di: Bridge sirve cuando algo varía en dos direcciones a la vez. Si solo cambia una cosa, sobra: agrega clases sin necesidad.

Señala: la línea de JDBC. Cambiando solo el texto de conexión, el mismo código habla con otra base de datos.

Consejo: si alguien conectó MySQL en el proyecto de base de datos, que diga que esa conexión ya fue un Bridge.

Consejo: no lo confundas con Adapter. Adapter arregla una incompatibilidad que ya existe; Bridge se planea desde el inicio para que dos partes varíen por separado.

Tiempo: 2 minutos. Termina dando paso a Carlos con Composite.

Composite

Trata igual a un elemento suelto y a un grupo de elementos organizados en árbol.

El problema en TechStore

El Kit Gamer contiene un PC, un mouse y un Kit Streaming, que a su vez trae micrófono y cámara. El carrito necesita el precio de todo.

Sin Composite tendríamos que:

  • Preguntar en cada paso si es producto o kit.
  • Escribir un ciclo por cada nivel del árbol.
  • Cambiar el carrito si aparece un kit dentro de otro.

Di: En el computador, una carpeta puede tener archivos y otras carpetas, y aun así le puedes preguntar cuánto pesa. En TechStore, los kits son esas carpetas.

Señala: el Kit Streaming dentro del Kit Gamer. Sin el patrón, el carrito tendría que saber cuántos niveles hay.

Tiempo: 2 minutos.

  1. Vista completaAvanza con la flecha para recorrer el patrón pieza por pieza.
  2. Paso 1 de 4Componente: la interfaz común. Productos y kits responden a getPrecio().
  3. Paso 2 de 4Hoja: un producto suelto devuelve su propio precio.
  4. Paso 3 de 4Compuesto: el kit guarda una lista de ítems y suma sus precios. Si un ítem es otro kit, este repite la suma: eso es recursión.
  5. Paso 4 de 4En TechStore: el carrito pide el precio del Kit Gamer y no le importa cuántos niveles tenga dentro.

Di: Producto y Kit implementan la misma interfaz, por eso el carrito los trata igual. En el paso 3 detente en la línea clave: si el ítem es otro kit, se vuelve a llamar getPrecio() adentro.

Señala: la lista List<ItemCatalogo>. Como guarda ItemCatalogo y no Producto, puede contener otros kits.

Consejo: usa el último paso para recorrer el árbol del diagrama con el dedo: Kit Gamer pregunta a PC, a Mouse y a Kit Streaming, que pregunta a los suyos.

Tiempo: 4 minutos.

Se usa con estructuras de árbol

  • Catálogos con categorías y kits
  • Menús con submenús
  • Carpetas y archivos

Ventajas

  • El cliente no distingue hoja de grupo
  • Agregar tipos nuevos es fácil

Desventajas

  • Cuesta limitar qué puede contener un grupo
  • Una interfaz muy general puede confundir

Un ejemplo de uso

En Swing, un JPanel contiene botones y también otros paneles: los trata a todos como componentes.

JPanel panel = new JPanel(); panel.add(new JButton("Pagar")); panel.add(otroPanel);

Di: Composite aparece en todo lo que tiene forma de árbol: menús, carpetas o pantallas hechas con paneles.

Señala: la última línea: un panel dentro de otro panel, igual que un kit dentro de otro kit.

Consejo: no lo confundas con Decorator. Los dos usan composición recursiva, pero Composite agrupa muchos hijos para formar un árbol; Decorator envuelve uno solo para añadirle algo.

Tiempo: 2 minutos. Termina dando paso a Yeison con Decorator.

Decorator

Añade funciones a un objeto mientras el programa corre, envolviéndolo en otro con la misma interfaz.

El problema en TechStore

Un pedido puede llevar empaque de regalo, garantía extendida y envío exprés, en cualquier combinación y en cualquier orden.

Sin Decorator tendríamos que:

  • Crear 7 subclases, una por cada combinación.
  • Llenar Pedido de if para cada extra.
  • Tocar Pedido cada vez que aparece un extra nuevo.

Di: Cuando pedimos un café con leche y crema, el café sigue siendo café; los extras lo envuelven. En TechStore, el pedido es el café y el regalo, la garantía y el envío exprés son los extras.

Señala: las 7 subclases. Con 3 extras hay 7 combinaciones posibles, y con un cuarto extra serían 15.

Tiempo: 2 minutos.

  1. Vista completaAvanza con la flecha para recorrer el patrón pieza por pieza.
  2. Paso 1 de 4Componente: la interfaz Pedido y el pedido base, que solo cobra el producto.
  3. Paso 2 de 4Decorador: Extra también es un Pedido y guarda dentro otro Pedido.
  4. Paso 3 de 4Extra concreto: le pide el total al pedido que envuelve y le suma su precio.
  5. Paso 4 de 4Uso: se envuelven como muñecas rusas. 120.000 del producto, + 15.000 del regalo, + el envío exprés.

Di: El truco está en que Extra es un Pedido y además guarda un Pedido. Por eso se pueden poner unos dentro de otros. En el paso 3, la línea clave le pregunta al de adentro y le suma lo suyo.

Señala: la última línea del código y las cajas del diagrama: se leen de adentro hacia afuera.

Consejo: si preguntan por el orden, los extras se pueden poner en cualquier orden y el total da lo mismo.

Tiempo: 4 minutos.

Se usa con extras opcionales

  • Extras de un pedido
  • Filtros sobre un flujo de datos
  • Permisos o registro sobre un servicio

Ventajas

  • Los extras se combinan en cualquier orden
  • Cada extra tiene una sola responsabilidad

Desventajas

  • Muchos objetos pequeños, difíciles de depurar
  • Quitar un extra del medio es complicado

Un ejemplo de uso

BufferedReader es un Decorator: envuelve al FileReader y le agrega leer por líneas, con la misma interfaz Reader.

new BufferedReader( new FileReader("datos.txt"));

Di: Java usa Decorator en toda su librería de archivos: cada clase envuelve a otra y le agrega algo.

Señala: la línea de BufferedReader. Es la misma que Deyvid mostró en Adapter: allí InputStreamReader adapta y BufferedReader decora.

Consejo: no lo confundas con Proxy. Los dos tienen la misma interfaz que el objeto que envuelven, pero Decorator añade funciones que el cliente elige; Proxy controla el acceso.

Tiempo: 2 minutos. Termina dando paso a Karen con Facade.

Facade

Da una sola puerta de entrada, sencilla, a un grupo de clases complicado.

El problema en TechStore

Para comprar hay que revisar el stock, cobrar y despachar, en ese orden y sin saltarse pasos. Hoy cada pantalla (web, app, caja) lo hace por su cuenta.

Sin Facade tendríamos que:

  • Repetir el orden de los pasos en cada pantalla.
  • Despachar algo que no se cobró si alguien se equivoca.
  • Cambiar todas las pantallas si el proceso cambia.

Di: Cuando llegamos a un hotel no buscamos al de limpieza ni al de las llaves: hablamos con la recepción. En TechStore, comprar exige tres sistemas y el orden importa.

Señala: el segundo problema: si una pantalla se salta un paso, se despacha algo sin cobrar.

Tiempo: 2 minutos.

  1. Vista completaAvanza con la flecha para recorrer el patrón pieza por pieza.
  2. Paso 1 de 3Subsistema: tres clases independientes. Para comprar hay que usarlas en orden: stock, cobro y despacho.
  3. Paso 2 de 3Fachada: CheckoutFacade guarda las tres y las llama en el orden correcto. La línea clave solo despacha si hay stock y el cobro pasó.
  4. Paso 3 de 3Cliente: la pantalla hace una sola llamada y no conoce el subsistema.

Di: Las tres clases de arriba no cambian. La fachada las guarda y en un solo método las llama en orden. En el paso 2 lee la línea clave: si hay stock y se pudo cobrar, entonces despacha.

Señala: la última línea: todo lo que la pantalla necesita saber es comprar().

Consejo: deja claro que el subsistema sigue disponible: la fachada no lo esconde ni lo prohíbe, solo simplifica el uso normal.

Tiempo: 4 minutos.

Se usa con procesos de muchos pasos

  • Checkout: stock, pago y despacho
  • Capa de servicios entre la pantalla y la lógica
  • Librerías complicadas de configurar

Ventajas

  • El cliente no conoce el subsistema
  • El orden de los pasos vive en un solo lugar

Desventajas

  • La fachada puede crecer hasta hacer demasiado
  • Puede esconder funciones avanzadas

Un ejemplo de uso

El botón de encender es una fachada: arranca CPU, memoria y disco con un toque. En software, la capa de servicios hace lo mismo entre la pantalla y la lógica.

// la pantalla solo conoce el servicio compraService.comprar(carrito);

Di: Facade aparece en cualquier proceso de varios pasos que queremos ofrecer como uno solo.

Señala: la línea de código: la pantalla no sabe nada de inventario, pago ni despacho.

Consejo: si el profesor pide un ejemplo en código Java: URI.create(url).toURL().openStream() abre la conexión, habla HTTP y entrega los datos en una sola llamada.

Consejo: no lo confundas con Adapter. Facade inventa una interfaz más simple para muchas clases; Adapter hace encajar una sola clase en una interfaz que ya existe.

Tiempo: 2 minutos. Termina dando paso a Deyvid con Flyweight.

Flyweight

Ahorra memoria compartiendo los datos que se repiten en muchos objetos parecidos.

El problema en TechStore

El inventario tiene 50.000 unidades de solo 20 modelos. Hoy cada unidad copia el nombre, las especificaciones y las fotos de su modelo.

Sin Flyweight tendríamos que:

  • Repetir los mismos datos 50.000 veces en memoria.
  • Volver lenta la carga del inventario.
  • Corregir un dato del modelo en miles de objetos.

Di: Cuando escribimos un texto, la letra «a» no se dibuja de nuevo cada vez: se usa la misma forma y solo cambia la posición. En TechStore, el modelo es la forma y cada unidad es una posición.

Señala: los números: 50.000 unidades pero solo 20 modelos distintos. Casi todo lo que guardamos está repetido.

Tiempo: 2 minutos.

  1. Vista completaAvanza con la flecha para recorrer el patrón pieza por pieza.
  2. Paso 1 de 3Flyweight: el modelo guarda lo que se repite (estado intrínseco) y nunca cambia.
  3. Paso 2 de 3Fábrica: guarda los modelos en un HashMap. Si el modelo ya existe lo devuelve; si no, lo crea una sola vez.
  4. Paso 3 de 3Unidad: guarda solo su serie y su bodega (estado extrínseco) y apunta al modelo compartido.

Di: Dos palabras para recordar: intrínseco es lo que se comparte, el modelo; extrínseco es lo propio de cada unidad, su serie y su bodega. En el paso 2, la línea clave busca el modelo antes de crearlo.

Señala: el diagrama de abajo: seis unidades apuntan a solo dos modelos.

Consejo: practica explicar intrínseco y extrínseco con la unidad de inventario. Es lo que más preguntan de este patrón.

Tiempo: 4 minutos.

Se usa con miles de objetos parecidos

  • Inventarios y catálogos masivos
  • Letras en un editor de texto
  • Árboles o balas en un videojuego

Ventajas

  • Reduce mucho el uso de memoria
  • Se crean menos objetos

Desventajas

  • El código se vuelve más complicado
  • Solo vale la pena con muchísimos objetos

Un ejemplo de uso

Integer.valueOf es un Flyweight: Java guarda los Integer entre -128 y 127 y devuelve siempre el mismo objeto.

Integer a = Integer.valueOf(100); Integer b = Integer.valueOf(100); a == b // true: es el mismo objeto

Di: Flyweight solo vale la pena cuando hay muchísimos objetos que repiten datos. Con pocos objetos solo complica el código.

Señala: a == b da true: Java no creó dos objetos, reutilizó el mismo.

Consejo: si preguntan por qué no basta con la base de datos: los datos ya están en la base, el problema es la memoria del programa cuando los carga todos a la vez.

Tiempo: 2 minutos. Termina dando paso a Anaya con Proxy.

Proxy

Pone un sustituto delante del objeto real para controlar quién accede a él y cuándo.

El problema en TechStore

El reporte de ventas tarda varios segundos en generarse y solo lo puede ver un administrador. Hoy se genera apenas abre el panel, lo vea alguien o no.

Sin Proxy tendríamos que:

  • Generar un reporte pesado que nadie va a abrir.
  • Revisar permisos dentro de la clase del reporte.
  • Mezclar la seguridad con la lógica del negocio.

Di: En un edificio, el guardia no es la oficina, pero está delante de ella: revisa quién entra. En TechStore pondremos un guardia delante del reporte de ventas.

Señala: los dos problemas: el reporte es lento y además es privado. Un proxy resuelve los dos.

Tiempo: 2 minutos.

  1. Vista completaAvanza con la flecha para recorrer el patrón pieza por pieza.
  2. Paso 1 de 4Sujeto: la interfaz Reporte. El panel solo conoce esta interfaz.
  3. Paso 2 de 4Sujeto real: ReporteVentas hace una consulta pesada apenas se crea.
  4. Paso 3 de 4Proxy: tiene la misma interfaz. Revisa el permiso y crea el reporte real solo la primera vez que alguien lo abre.
  5. Paso 4 de 4Cliente: el panel llama mostrar() igual que siempre. No sabe que habla con un sustituto.

Di: El proxy implementa la misma interfaz que el reporte real, por eso el panel no nota la diferencia. En el paso 3: primero revisa el permiso, y la línea clave crea el reporte pesado solo cuando de verdad se necesita.

Señala: el atributo real que empieza en null. Mientras nadie abra el reporte, la consulta pesada nunca se hace.

Consejo: nombra los tipos de proxy: virtual (carga diferida), de protección (permisos), remoto, de registro y de caché. El de TechStore es virtual y de protección a la vez.

Tiempo: 4 minutos.

Se usa para controlar el acceso

  • Cargar imágenes solo cuando se ven
  • Revisar permisos antes de abrir algo
  • Registrar quién usa un servicio

Ventajas

  • Controla el objeto real sin que el cliente lo note
  • Agrega permisos o carga diferida sin tocar la clase real

Desventajas

  • Una capa más que puede hacer lenta la respuesta
  • Más clases que mantener

Un ejemplo de uso

Las fotos de una tienda en línea se cargan solo cuando aparecen en pantalla. Mientras tanto, un proxy ocupa su lugar.

Imagen foto = new ImagenProxy("x1.jpg"); foto.mostrar(); // recién aquí descarga

Di: Proxy se usa siempre que algo es caro de crear o delicado de usar. Las fotos de una tienda en línea que cargan solo al bajar con el scroll son un proxy virtual.

Señala: las dos líneas: crear el proxy es inmediato; la descarga pesada ocurre al mostrar la foto.

Consejo: si preguntan por un ejemplo en Java: Hibernate entrega un proxy en vez del objeto real y solo consulta la base de datos cuando se usa.

Consejo: no lo confundas con Decorator. Proxy controla el acceso y él mismo decide cuándo crear el objeto real; Decorator añade funciones que el cliente elige.

Los que más se confunden

Adapter o Facade

Adapter adapta una clase a una interfaz que ya existe.

Facade crea una interfaz nueva y más simple para muchas clases.

Decorator o Proxy

Decorator añade funciones que el cliente elige.

Proxy controla el acceso y decide cuándo crear el objeto.

Composite o Decorator

Composite agrupa muchos hijos en un árbol.

Decorator envuelve uno solo para sumarle algo.

Bridge o Adapter

Bridge se planea desde el diseño para que dos partes varíen.

Adapter arregla después una incompatibilidad que ya existe.

Di: Estos cuatro pares se parecen porque todos envuelven o conectan objetos. La diferencia está en para qué lo hacen.

Señala: las palabras en negrita: una, nueva, añade, controla, muchos, uno, planea, arregla.
